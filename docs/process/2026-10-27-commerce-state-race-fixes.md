# 授权交付、到期提醒与支付退款状态修复

后续状态：本批修复及0052迁移已于2026-10-27经用户批准上线；微信支付保持关闭。下文保留实现时的验证边界，生产结果与回滚证据见[上线记录](2026-10-27-license-fixes-release.md)。

状态：本地实现与隔离验证；未执行生产迁移、真实退款、渠道查单或通知邮件。当前生产的只读检查显示微信未配置且无微信订单，支付宝已配置；不把可执行代码缺陷等同于已发生生产退款事故。没有对账渠道账单。

## 三项修复

1. 父授权创建改为数据库唯一约束下的 `INSERT ... ON CONFLICT DO NOTHING RETURNING`，冲突后回读同一订单的赢家。回调发码与账户自动补码交错时，不再因 `order_id` 唯一冲突将交付标为 failed；随机码碰撞仍有有界重试，不覆盖原授权状态。
2. Pass 提醒按邮箱归并有效订单和历史 INV 来源，使用与权益计算相同的 `accumulatePass`，按来源 ID 去重后判断最终到期窗口。永久授权不再被旧月付触发提醒；提前续费保留余期。
3. 微信与支付宝共用 `payment_refund_attempts` 记录退款请求号、支付渠道、金额、状态与查询时间。只有已验证的全额退款成功才在同一事务内将订单设为 refunded、父授权设为 revoked。申请受理、PROCESSING、ABNORMAL、网络未知均不抢先收回付费权益。
4. 支付宝只有已验签且交易/金额匹配的 `fund_change=Y` 可直接确认；N、缺失、网络或系统异常进入未知状态，之后以查询返回 `REFUND_SUCCESS` 确认。本站全额退款显式使用 orderId 作为 out_request_no，与旧接口省略时的渠道默认号一致。

## 退款状态边界

- `SUCCESS` 保持成功，包括部分退款的成功记录；迟到的 CLOSED/ABNORMAL/PROCESSING 不能覆盖。
- ABNORMAL 需要人工处理，之后可进入 SUCCESS；不能把它当成退款失败并恢复授权。ABNORMAL 回调先于申请响应到达时，旧 PROCESSING 快照不会清除人工核验标记。
- 未知或拒绝后的重试沿用原请求号，先查单；微信仅在渠道确认 CLOSED 后允许新建另一笔尝试。并发管理员操作共用订单级事务锁。lastRequestedAt/lastQueriedAt在同一锁内认领，支付宝至少间隔10秒，微信按建议至少60秒，连点不会重复查询或重发。
- 已标refunded但没有尝试记录的历史支付宝订单，只按orderId建立legacy查询记录，绝不重发退款或自动恢复paid；无法证实结果时保持人工核验。没有新建自动查询cron，查询由后台核对按钮触发。
- 商户平台直接发生的全额退款可通过已验签回调登记并生效；部分退款仅登记人工核验，不自动改变整份商品权益。
- 管理员原先手动撤销的许可证不会被失败通知恢复。旧 `refunded` 订单没有尝试记录时，失败回调只登记人工核验，不能猜测它是成功退款还是旧代码的临时标记。
- 申请 HTTP 异常发生在 SUCCESS 回调之后，仍以持久成功事实为准，不补偿回 paid。查询不可达时保留未决记录与原权益，不另起退款号。
- 退款请求使用现有正式回调 URL；响应验签，并核对商户、退款号、交易号和金额。后台显示处理中/未知/人工核验，未决时提供同一退款的核对入口。

依据：[支付宝退款接口](https://aipay.alipay.com/docs/subscribe/api-list/other-basic-interfaces/alipay-trade-refund.html)、[支付宝退款查询](https://aipay.alipay.com/docs/vibe-pay/ai-web-app-payment-qianyi/api-list/alipay-trade-fastpay-refund-query.html)、[微信退款开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4013071031)、[退款申请接口](https://pay.wechatpay.cn/doc/v3/merchant/4013071036)、[退款通知协议](https://pay.wechatpay.cn/doc/v3/merchant/4013071196)。这些官方规则要求区分受理与最终退款、持久化退款状态，并在异常或超时时使用原退款号确认结果。

## 迁移与回滚

`0052_payment_refund_attempts.sql` 仅增加 `payment_refund_attempts` 一张表（13列，包含paymentMethod和两种请求时间）、订单外键、状态/渠道/金额检查和订单时间索引；不增加 orders 列，不改写旧订单或许可证。后台返回的 `refundStatus` / `outRefundNo` 是查询 DTO 字段。

计划上线顺序：备份与核对当前迁移账本 → 确认仅本迁移待执行 → 执行标准迁移器 → 验证表、约束和账本 → 部署应用 → 只读健康验证。迁移未执行前不能发布引用新表的后台/回调代码。本轮未执行这些生产步骤，也未启用微信支付。

回滚保留新表及退款尝试记录，不能通过恢复旧数据库覆盖新交易。尚未产生新退款尝试时可回退应用；一旦存在未决或成功尝试，必须保留修复后的回调/查询处理，或暂停新退款入口并完成渠道核验，不能退回会把旧失败事件当作恢复授权指令的处理器。历史不明状态与部分退款必须人工核对，不能自动批量修账。

微信当前仍有独立的启用阻碍：现有下单号使用36位UUID，超过微信该接口32字符约束；本轮未改变已停用的创建支付流程、未启用微信，不能声称微信已具备完整上线条件。

## 验证层级

- 真正的本地 PostgreSQL：使用测试专属 trigger + advisory barrier 固定“付款发码查空 → 页面补码提交 → 付款 INSERT”顺序，验证交付成功、仅一个父码且邮件交付使用赢家；不是重复调用同一个补码函数。
- 真正的本地 PostgreSQL：退款多尝试乱序、成功回调先于 HTTP 异常、ABNORMAL 后续成功、手动撤销、部分退款、未决重试和并发创建。
- 本地 RSA/AES 夹具：微信通知验签解密、商户/事件/金额绑定、响应验签、notify_url 和稳定退款号；支付宝按原始JSON对象串验签、交易/请求号/金额绑定、资金变更与查询成功判断；HTTP 均被模拟。
- 提醒与管理界面回归：累计到期、永久授权、订单+INV、未决状态不假称已退款。
- 所有邮件调用均被 mock。本地测试不替代真实扣款、真实退款、商户配置或生产回调验收。
