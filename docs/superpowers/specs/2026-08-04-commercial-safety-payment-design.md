# Meteor Store 商业安全与支付闭环设计

> 日期：2026-08-04
> 状态：已按用户“全部采用推荐方案并直接执行”的授权确认

## 目标

在不猜测未来订阅产品形态的前提下，先让生产环境停止接受新订单，并修复一次性支付宝订单从创建、异步通知、同步回跳、授权生成到邮件交付的完整链路。完成真实沙箱或小额生产验收前，不重新开放销售。

## 方案比较

### A. 先关闭销售，再完成可靠的一次性订单闭环（采用）

- 优点：立即停止不完整链路继续产生订单；改动可测试、可回滚；不需要先实现完整订阅平台。
- 代价：修复期间不能购买；月付、年付和额度产品继续保持关闭。

### B. 直接实现自动续费订阅

- 优点：与当前文案最一致。
- 代价：需要签约代扣、订阅状态机、账期、取消、退款、额度计量和产品端鉴权，范围远超本轮故障修复。

### C. 只修页面回跳

- 优点：改动最少。
- 代价：异步回调域名、重复交付、授权模型和商业承诺仍然不可靠，不能视为生产可用。

## 边界与数据流

### 1. 销售总开关

生产 `NEXT_PUBLIC_SHOW_PRICING=false`。这是构建期变量，更新后必须重新部署。回滚只需把变量恢复为 `true` 并重新部署，但仅在沙箱/真实小额支付验收通过后执行。

### 2. Canonical 站点地址

生产 `NEXT_PUBLIC_SITE_URL` 统一为 `https://www.imagentx.top`。支付配置在服务端解析并校验该 URL，禁止生成需要 308 跳转的 `notify_url`。

### 3. 支付宝回跳

- `notify_url`：固定指向 canonical 域名下的异步 POST route。
- `return_url`：固定指向独立同步回跳 route，不再直接进入成功页。
- 同步 route 验证支付宝签名和订单号；验证成功后签发短时、HttpOnly、SameSite=Lax 的订单查看凭证，再跳到干净的 `/success?orderId=...`。
- 成功页通过登录邮箱或短时订单凭证访问，不在 URL 暴露持久 `accessToken`。
- 异步通知仍是支付状态的唯一可信来源；同步回跳只能展示“处理中”，不能自行把订单改成已支付。

### 4. 订单交付

新增统一 `fulfillOrder(orderId)` 服务：

1. 只接受 `paid` 订单。
2. 用条件更新把 `pending/failed` 原子认领为 `processing`。
3. 幂等创建一把授权码。
4. 发送订单确认邮件。
5. 成功置为 `emailed`，失败置为 `failed`。

免费方案不再经过订单 API 发授权码；前端继续直接进入公开下载，API 对零价方案返回明确错误，避免不可达的免费订单分支和批量发码。

### 5. 当前不做

- 不实现自动续费、配额计量、设备激活和产品端授权校验。
- 不重新开放销售。
- 不在本批修改邀请码、R2、学生认证和账户注销；它们按后续批次单独处理。

## 错误处理

- 支付配置缺任一必要字段时，下单返回 503，不创建数据库订单。
- 同步回跳签名无效或订单不存在时，跳转到无订单凭证的失败页面，不泄露订单信息。
- 异步通知验签、app_id、seller_id、金额任一不符时拒绝更新订单并告警。
- 交付失败保留已支付订单和幂等授权码，管理员可安全重试，不重复生成授权。

## 测试

- 支付创建：销售关闭、配置不完整、零价方案、正常订单。
- URL：canonical `notify_url/return_url` 不发生跨域跳转。
- 同步回跳：有效签名签发凭证；无效签名不泄露订单。
- 成功页访问：登录邮箱或短时凭证可看；只有订单号不可看。
- 交付服务：只有一个并发调用能认领；失败可重试；成功不重复发信。
- 现有支付宝异步通知、邮件、授权、类型、Lint、全量测试和构建全部通过。

## 上线与回滚

1. 先关闭销售并部署。
2. 合并代码与必要迁移，保持销售关闭部署。
3. 用支付宝沙箱验证完整链路。
4. 如需生产验收，创建一笔最小金额订单并立即核对回调、邮件、订单页和授权；验收记录随后退款或清理。
5. 只有验收通过且经营信息完成后，才恢复销售开关。
