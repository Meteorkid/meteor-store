先说结论，免得浪费时间：

**给 AI 编程助手做外部面板，能做和不能做之间的分界线，不是「有没有事件通知」，是「有没有原生审批回传」。**

这条线画错，产品会变成一堆点了没反应的按钮。我在 macOS 上写了个悬浮面板（灵动岛形态）接这类客户端，前后踩了几个月，下面这些是真实遇到的，不是设计推演。

## 一、通知 ≠ 批准，这两件事差一个语义层级

最容易犯的错，是看到某家客户端有 notification / hook 事件，就顺手在上面挂一个「允许」按钮。

Gemini CLI 有通知通道，但通知不是审批接口。你把按钮接到通知上，用户点了「允许」，客户端那边还在等它自己的确认——表现就是「我点了但没生效」。这比不做还糟，因为用户会认为软件是坏的。

Windsurf / Cascade 的前置 hook 可以拦一次调用，但拦住的语义是「我阻止了」，不等于「我允许了」。拿阻断去冒充批准，结果是工具直接跑不起来。

Factory Droid 我只核到观察类事件，没有可用的 PermissionRequest。那就一个审批按钮都不放。

**做法上我最后收敛成三层能力，UI 按层降级：**

| 层级 | 能力 | UI 表现 |
|---|---|---|
| 观察 | 知道会话在跑 / 在等 / 报错 | 状态灯、标题、活动流 |
| 应答 | 代理提问能回传（单选 / 多选 / 文本） | 岛上出现选项 |
| 审批 | 决定作为**原生批准结果**交回 | 出现「允许 / 拒绝」 |

低于哪一层，就不显示哪一层的交互。**宁可不给，也不给假的。**

## 二、「配置文件写好了」和「接通了」是三件事

生成 hooks 配置 → 客户端加载 → 用户信任这些 hooks。

各家普遍有第三层：你写了配置，它还要你手动进去点一次「允许」。这层不做，文件再对也没有事件进来。

所以状态机不能是「已连接 / 未连接」两档。我改成六档：

```
待配置 / 待授权 / 待完成设置 / 等待活动 / 已接入 / 检查失败
```

其中最重要的是「等待活动」和「已接入」必须分开：配置文件存在、进程起来了、开关打开了，全都只到「等待活动」。**必须收到一条真实任务产生的事件，才允许显示「已接入」。**

配套两条纪律：

1. 有只读查询接口就去查真实状态，别猜。Codex 能读 hooks 列表，拿到启用状态、信任状态和定义指纹；查不到就显示「检查失败」，不写成「未授权」也不写成「已授权」。
2. 不写别人的信任记录，也不批量信任其他 hooks。用户可能自己有一堆 hooks 在跑，替他勾「全部信任」是在改他的安全边界。

## 三、同一个品牌不等于同一套协议

这条吃过大亏，现在矩阵是按「客户端 × 形态」一格一格填的：

- Trae CN 和国际版两套协议，CN 的验收结果不能挪过去
- Cline 的 VS Code 扩展和它的 SDK CLI 是两条路，扩展通了不代表 CLI 通
- Zed / JetBrains 的内置 AI 拿不到外部通道，能接的只是**显式启动的外部 ACP Agent**，权限留在编辑器里
- Continue 只能靠 `serve /state` 轮询快照，会漏短暂状态，能用但不精确

CLI、IDE 插件、桌面端分开记，一格验过不代表隔壁。这条听起来啰嗦，但矩阵里如果偷懒合并，最后一定会在某个用户那里翻车。

## 四、会话身份：认错会话比没有会话更糟

事件收上来只是开始，还得判断它属于哪个会话。各家线索完全不同：Windsurf 用 `trajectory_id`，Kimi 有任务树，Qoder 区分原生会话和子任务，Copilot CLI 有并发 ID 要消歧，Roo Code 会有多窗口来源。

还有一类没有稳定 ID：Amazon Q 的旧 CLI 包装器拿不到稳定的调用标识和回复正文，那就只做进程级观察，不碰内容。

认错会话的后果是：代理 A 的问题显示在代理 B 的卡片上，你点了个允许，批的是另一件事。所以身份不确定时，我选择不显示交互。
