## 先说结论

「同时跑多个 AI 编程代理，怎么不丢掉权限确认」这个问题，**根因不在代理，在于确认请求是「推给终端」而不是「推给你」**。

代理请求权限时，它把提示写进了自己那个终端会话。你人不在那个窗口前，提示就一直挂着。代理不会超时失败，也不会重试，它只是停在那里——直到你想起来切回去。

所以管这件事只有三个方向：**减少并发**、**让代理自己跑**、**把确认请求从终端里拿出来**。三种我都试过，下面把代价写清楚。

## 为什么会卡住：一次真实的时间线

假设你在跑四个会话：

```
窗口 1  Claude Code   重构 auth 模块        → 正在跑
窗口 2  Claude Code   补测试                → 等你批准写文件
窗口 3  Codex         修一个 lint 错误      → 正在跑
窗口 4  Gemini CLI    查一个 API 用法       → 等你回答一个问题
```

你去写了两小时代码，回来发现：

- 窗口 2 的代理从 40 分钟前就在等一个「是否允许修改 src/auth/session.ts」
- 窗口 4 的代理在等一个「你希望我用哪个 HTTP 客户端」

这两条加起来，两小时里实际只有两个代理在干活。

**注意这不是 bug。** 代理的行为完全正确：它要动你的文件，所以问你；它信息不足，所以问你。问题出在**问的方式和你的注意力不在同一个地方**。

## 三种管法，以及各自的代价

### 方法一：降低并发数

最省事的办法是别一次开那么多。

- **代价**：直接放弃并行带来的时间收益。如果你本来就只开一两个会话，那这个方法对你来说不是「代价」而是「正解」——**并发超过三个之前，不需要任何工具**。

### 方法二：给代理更大的自主权

用跳过权限确认的开关，或者配置白名单，让它别问。

- **代价**：这是**安全边界的整体让渡**，不是效率优化。跳过权限确认意味着代理可以不经你同意改文件、执行命令。在只读或可回滚的场景（干净的 git 分支、容器里）可以接受；在你的主工作目录上不行。
- 折中做法是**白名单而不是全跳过**：只放行读操作和特定路径的写操作，保留对删除、网络请求、执行任意命令的确认。但白名单需要维护，配置本身会变成新的负担。

### 方法三：把确认请求从终端里拿出来

这是我在做的事：用一个常驻面板订阅各家的 hook 事件，权限请求直接出现在屏幕上，你在那里点允许或拒绝，结果作为**原生批准结果**回传给客户端。

- **代价**：**能力受限于各家客户端的接口**，而且差异极大。这一点下面单独说——它是这个方法最大的坑，也是最容易被忽略的部分。

## 方法三的坑：不是每个客户端都允许「从外部批准」

如果你打算自己写个面板，或者评估现成工具，**先分清三层能力，它们不是一回事**：

| 层级 | 能力 | 普遍程度 |
|---|---|---|
| 能观察 | 收到事件，知道哪个会话在跑、在等、报错了 | 几乎都能做 |
| 能应答 | 代理提问时把答案回传 | 部分能做 |
| 能审批 | 权限请求在外部决定，并作为原生批准结果交回 | 少数能做 |

**分水岭在第三层。「我收到了一个通知」和「我能替用户批准」是两件不同的事，差一个语义层级。**

实际踩到的几种情况：

- **通知不能当批准依据。** 有的客户端有通知通道，但通知本身不是批准接口。你把面板按钮接到通知上，客户端那边依然在等它自己的确认——用户看到的是「我点了允许但没生效」。
- **有的客户端根本没有权限请求事件。** 这时正确的做法是**不显示任何审批按钮**。提前放一个假的「允许」，等于让用户对着一个不会生效的开关点。
- **「阻断」不等于「批准」。** 前置 hook 能拦住一次调用，但拦住的语义是「我阻止了」，不是「我允许了」。用阻断冒充批准，结果是工具跑不起来，用户以为软件坏了。
- **没有安全应答通道就不做应答。** 能读任务状态但没有可靠回写路径的，就只显示状态，审批留在编辑器里。

这里有一条我认为比功能数量更重要的原则：**接口不支持，就不要在 UI 上假装支持。** 用户能容忍「这个功能我这里没有」，不能容忍「点了没反应」。

## 还有个反直觉的地方：配置存在 ≠ 接通了

自己写配置的时候会踩到：**生成一份 hook 配置、它真的被加载、它真的被信任，是三件事。**

多数客户端还有一层信任确认——你写了配置，它还要你手动进去点一次「允许这些 hooks」。这层不做，文件写得再对也没有事件进来。

所以状态不能只做「已连接 / 未连接」两档。比较诚实的分法是六档：

```
待配置      配置不完整
待授权      客户端明确报告尚未信任
待完成设置  需要导入插件 / 选启动入口 / 连外部服务
等待活动    配置已就绪，但还没收到真实事件
已接入      收到过有效活动
检查失败    读不到授权状态
```

关键是**没有「等待活动」到「已接入」的自动推定**。配置文件存在、进程起来了、开关打开了，全都只到「等待活动」；必须收到一条真实任务产生的事件，才允许显示「已接入」。

## 会话身份：认错会话的后果比丢消息严重

把事件收上来之后，还得知道**这条事件属于哪个会话**。各家的身份线索都不一样：有的用 trajectory id，有的用任务树，有的区分原生会话和子任务，有的并发 ID 需要消歧，还有的会有多个窗口来源。

认错会话的后果很难看：**代理 A 的问题显示在代理 B 的卡片上，你点了个允许，批的是另一件事。**

有一类客户端干脆拿不到稳定 ID，那就只做进程级观察，不碰内容——**宁可少做，不要做错**。

## 回到你的问题

如果你现在正被这件事困扰，按这个顺序判断：

1. **并发不超过三个** → 不需要工具。把终端窗口排好，用系统自带的通知就够。
2. **需要更多并发，且能接受安全边界让渡** → 白名单配置，但记住你放弃的是什么。
3. **需要更多并发，且不能放弃安全** → 找一个能做「外部批准」的面板。**评估时别问「支持哪些客户端」，要问「哪些客户端能从外部真正批准，哪些只能看」**——这两者的差别决定了它是帮你干活还是给你添乱。

第 3 条我在做，覆盖 30 多个客户端形态，接入矩阵和每一格的验证记录都公开在仓库里。表格里写的是「验到哪一步」，不是「支持 / 不支持」——我宁可这份表看起来难看，也不想让人装完发现某一行是假的。

## 一个仍然没解决的问题

**多个代理同时请求权限时怎么排优先级**，我还没有好答案。现在的做法是全部平铺展示，谁先来谁在上面。但真实场景里，「改一个变量名」和「删除整个目录」的紧急程度显然不同，而当前的做法不区分。
